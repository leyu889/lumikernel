# 08 · 规模对标：为什么"代码量比不上 Linux"不是缺陷

> 写这份文档的原因：这是一个每隔一段时间就会被问一次的问题。
> 答案不靠辩解，靠三张表——**同口径对比**、**历史对位**、**差距构成**。

## 零、先认账

| | 代码行 | 含注释与空行 | 统计口径 |
|---|---:|---:|---|
| LumiKernel 内核本体 | **27,528** | 37,465 | `lumikernel/src` + `crates/*`，去注释去空行 |
| 工具 / 基准 / 引导 | 8,420 | 11,036 | `tools/` `scripts/` `bench/` `boot/`，不计入内核 |
| **合计** | **35,948** | 48,501 | |
| Linux 6.12 | **26,407,571** | — | sloccount 物理行（不含空行与注释） |
| 比值 | **1 : 959**（内核本体） | — | |

2.75 万行对 2640 万行，差**九百多倍**。这个事实不需要粉饰。

（全部数字可用 `python tools/loc.py` 复算。文档里另有 **6,484 行注释**——
本项目要求每个 `unsafe` 块、每个不显然的决定都写"为什么"，这部分不计入代码行。）

但"差多少倍"是个没有信息量的数字。有信息量的是**差在哪些子系统上，倍数分别是多少**。

## 一、同口径对比（按 Linux 的目录划分，对齐后的真实倍数）

| 子系统 | Linux 6.12 | LumiKernel | 倍数 | 差距的**性质** |
|---|---:|---:|---:|---|
| IPC / fd / VFS | 6,875 | 923 | **7.4×** | 纯逻辑 |
| 内存管理 `mm/` + 页表/堆/slab | 126,769 | 2,878 | **44×** | 纯逻辑 |
| 调度 + 中断 + 时间 `kernel/` | 319,187 | 2,952 | **108×** | 纯逻辑 + 策略 |
| 文件系统 `fs/` | 1,166,669 | 2,987 | **391×** | **60+ 种文件系统** |
| 架构 `arch/` | 1,777,035 | 1,415 | **1,256×** | **30+ 种 CPU 架构** |
| 驱动 `drivers/` | 18,548,831 | 952 | **19,484×** | **几十万种硬件组合** |
| 网络 `net/` | 942,831 | 0 | **∞** | 未实现 |
| 声音 `sound/` | 1,205,419 | 0 | **∞** | 不做 |

这张表里最重要的一列是"性质"：

**倍数最小的地方（IPC 7.4×、内存 44×）恰好是内核最难的逻辑；
倍数最大的地方（驱动 19,484×）恰好是最机械的硬件枚举。**

Linux 的 2640 万行里，**70% 是驱动，6.7% 是体系结构，两者合计 77%**。
剩下 23% 里还有声音、工具、文档。

真正的"内核核心"（调度 + 内存 + IPC + 进程模型）约 45 万行，
**占总量 1.7%**——而业界的共识是这 1.7% 承载了 95% 的复杂度。

所以更准确的说法是：

> 我们在**那 1.7%** 上做到了 Linux 的 1/7 到 1/108；
> 在**那 77%** 上做到了 1/1.9 万。
> 后者不是"写得糙"，是"只支持一种硬件配置"。

## 二、历史对位：同期规模下能干什么

数据来源：Tanenbaum 所在 VU 的源码对比表 + `cloc` 统计。

| 内核 | 年份 | C 代码行数 | 当时能做的事 |
|---|---|---:|---|
| Minix 1.1（内核） | 1987 | 11,386 | 多任务、Minix 文件系统 |
| Linux 0.01 | 1991.9 | 7,574 | 打印 A、读键盘；**只能跑在 AT 硬盘上** |
| Linux 0.11 | 1991.12 | **10,232** | 能跑 bash、能自己编译自己（自举） |
| Linux 0.12 | 1992.2 | 14,059 | 换成 GPL、加虚拟内存雏形 |
| Linux 0.96c | 1992 底 | 29,418 | 能跑 X Window |
| xv6（MIT 教学） | 2006 | 7,890 | 教学用，跑 6 个用户程序 |
| **LumiKernel** | 2026 | **27,528** | busybox sh、ext2 只读、LumiFS 可写、自研 AHCI、UEFI+BIOS 双引导、58 自检、281 单测 |

**结论：纯内核逻辑 2.75 万行，落在 Linux 0.11（1.02 万）与 0.96c（2.94 万）之间，靠近后者。**

这个对位要立刻跟一句诚实的限定：

- 2.75 万里有 **1,224 行是质量工程**（`kqa` + `kfault` + `qa.rs`）、
  **2,024 行是 Linux ABI 适配层**（`klinux`）——**这两块 Linux 0.1x 完全没有**。
  扣掉它们，可比的"内核功能面"约 **2.4 万行**。
- 另有 **6,484 行注释**不计入（本项目要求每个 `unsafe` 块、每个不显然的决定写"为什么"）。
  这是行数通胀里唯一正当的一种：它降低的是审计成本。
- 那个年代的 Linux **不需要**考虑 UEFI、SATA/AHCI、ACPI、APIC、SMP、
  4 级页表、Rust 的所有权约束。同等行数在今天意味着更少的"功能面"。

## 三、为什么这个差距不可能也不需要抹平

Linux 6.12 的 sloccount 输出里自带 COCOMO 估算：

```
Development Effort Estimate  : 8,787 人年
Schedule Estimate            : 16.9 年
Estimated Average Developers : 520 人
Total Estimated Cost         : 11.9 亿美元
```

而且这 2640 万行里 **84.3% 的提交由企业贡献**（2015 年以来 Intel、Google、Red Hat、
Meta 等 1,780 多家公司），因为它们各自的硬件要进内核。

换句话说：**Linux 的代码量是"硬件厂商的联合产品"，不是"内核设计的产物"。**
一个人（或一个团队）去追平这个数字，等于替整条 PC 产业链重做一遍硬件适配——
既不可能，也没有意义：那些工作已经存在，可以直接复用（UEFI 协议、ACPI 表、
甚至 Linux 驱动本体）。

## 四、真正的标准是什么

行业里判断一个内核"够不够格"，量的是这几件事，而不是行数：

| 维度 | Linux | LumiKernel | 判定 |
|---|---|---|---|
| 能跑未修改的真实程序 | ✅ 全部 | ✅ busybox sh（静态 musl） | **过** |
| 自有驱动（不借固件代劳） | ✅ 数百种 | ✅ AHCI/SATA 一种 | 规模不足，能力成立 |
| 自有文件系统（可写） | ✅ 60+ 种 | ✅ LumiFS（日志式） + ext2 只读 | **过** |
| 崩溃可定位 | ✅ kdump/ftrace | ✅ 转储 + 四级页表 + 栈回溯（<30 min 定位到根因） | **过** |
| 故障注入 / fuzz | ✅ 有框架 | ✅ 3 个注入点 + 2.5 万次 fuzz | **过** |
| 长时间跑不漏 | ✅ 数十年验证 | ✅ 1812 s / 63 亿次操作零漂移 + 负对照 | 时长不足，结论成立 |
| 他人可复现 | ✅ | ✅ 一条命令构建；281 单测全绿 | **过** |
| 硬件覆盖面 | 几十万种 | **1 种** | **明确的短板** |
| 网络栈 | 全栈 | **0** | **明确的短板** |
| SMP 规模 | 4096 核 | 2 核 | **明确的短板** |

**六项"过"、三项"短板"，而且短板全部集中在"覆盖面"上，没有一项在"可靠性"上。**

这正是 `docs/00-定位与稳定性哲学.md` 里定的目标：不比 Linux 支持得多，
只比 Linux **在受支持范围内更不容易崩、崩了更能定位**。

## 五、如果要扩，按什么顺序扩

原则：**按"能换来的可验证能力"排序，不按行数排序。**
写代码凑行数是最糟的工程决策——它会同时降低可审计性和可靠性。

| 顺序 | 做什么 | 预计行数 | 换来的能力 | 为什么排这个位置 |
|---|---|---:|---|---|
| 1 | 网络栈（`net/`）：ARP/IPv4/ICMP/UDP/TCP + 一个 e1000 驱动 | +6,000 | `ping`/`nc` 可用，能当真实主机 | 唯一"完全为 0"的核心子系统；行数/能力比最高 |
| 2 | `fork` COW + `mmap` 懒分配 | +800 | 与 Linux 同策略，性能可直比 | 目前两项差 14–200 倍是**策略差异**，改完才是真对比 |
| 3 | ext2 读写 + 更多 fs（FAT32 / 只读 NTFS） | +3,000 | 能挂真实 U 盘 | 覆盖面短板里最实用的一项 |
| 4 | virtio-blk / virtio-net / NVMe 驱动 | +2,500 | 在 KVM/QEMU 上原生跑 | 摆脱"只支持 VBox 的 AHCI"这个环境限制 |
| 5 | SMP 扩展到 8 核（per-CPU 数据 + 细粒度锁） | +2,000 | 真实多核压测 | 需要先做 2，否则 COW 与 per-CPU 冲突 |
| 6 | 更多体系结构（RISC-V 64） | +15,000 | 证明"不是 x86 专用" | 性价比最低，但最能证明架构分层是真的 |

做完 1–5，内核本体约 **4.2 万行**——仍然只有 Linux 的 1/630，但能力面覆盖
"能当一台能联网、能挂 U 盘、能多核跑的真实主机"。

**这个目标是可以达成的；"2640 万行"不是。**

## 六、一句话结论

> 行数衡量的是**覆盖面**，不是**工程质量**。
> Linux 的 2640 万行里 77% 在为硬件兼容性买单，那部分应该复用而不是重写。
> 我们的 2.75 万行在"调度 / 内存 / IPC / 崩溃定位 / 稳定性验证"上做到了
> Linux 的 1/7 到 1/108，并且**每一项都有脚本和数字**。
> 短板是网络、硬件覆盖、SMP 规模——这三项有明确的补齐路线，见上表。
