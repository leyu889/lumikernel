# 01 · 架构：宏内核

## 一、形态：跟 Linux 同构的宏内核

驱动、文件系统、网络协议栈、调度、内存管理**全部在内核态**，共享一个地址空间。
不为"隔离"把服务赶到用户态——那样 IPC 开销和复杂度都会吃掉性能，而且和 Linux 的生态模型对不上。

```
┌──────────────────────────────────────────────────────────────┐
│ 用户态：init / shell / 服务程序 / Linux 二进制（将来）          │
├──────────────────────────────────────────────────────────────┤
│ 系统调用层（syscall）：文件、进程、内存、网络、时间             │
├──────────────────────────────────────────────────────────────┤
│ 内核态（单一地址空间，分层，不许跨层反向依赖）                  │
│                                                              │
│  VFS ── ext2 / LumiFS / proc / devfs ── 页缓存 ── 块层         │
│  socket ── TCP/UDP/IP/ARP ── netdev ── e1000 / virtio-net      │
│  调度器 ── 线程/进程 ── 信号 ── 定时器                          │
│  MM：物理帧 / 页表 / slab / vmalloc / COW / 换页（后期）        │
│  驱动：PCIe / ATA / AHCI / NVMe / USB / 输入 / 显示             │
└──────────────────────────────────────────────────────────────┘
```

**和 Linux 的差别不在形态，在纪律**：
1. 内核用 Rust，`unsafe` 只出现在必须碰硬件的边界；
2. 分层是强制的（`arch → mm → kernel → fs/net/drivers`，只能向下调用）；
3. 每个子系统可单独在宿主机上跑单元测试（硬件通过 trait 注入 mock）；
4. 任何"静默失败"都算 bug：内存不足、设备超时、队列满，必须是显式返回值。

## 二、为什么宏内核也要讲"稳定"

宏内核的天生弱点是**一颗老鼠屎坏一锅汤**：驱动空指针，整机崩。既然选了宏内核，稳定性必须从别处补：

| 手段 | 作用 |
|---|---|
| Rust 内存安全 | 消掉缓冲区溢出 / UAF / 数据竞争这几类最常见的驱动崩溃 |
| 分层与接口收窄 | 驱动只能通过 `BlockDevice` / `NetDev` / `IrqGuard` 这些窄接口碰内核，减少踩坏别人的可能 |
| 显式错误传播 | 任何失败都返回 `Result`，不允许 `unwrap`；OOM 不 panic |
| 运行时自检（debug 构建） | 红黑树/链表/页表操作带不变量断言，早期暴露状态机错误 |
| 看门狗与崩溃现场 | 内核 panic 前把寄存器、栈回溯、当前任务、锁持有者写串口；重启后能定位到函数 |
| IOMMU | 驱动 DMA 越界被硬件拦住（M5 之后） |
| 长跑与故障注入 | 分配失败、DMA 边界、坏块、断链、信号风暴，全部变成可重复的测试用例 |

**不承诺**"驱动崩了系统还活着"——宏内核做不到，硬说就是骗人。承诺的是：
**驱动崩溃的概率更低（内存安全），崩溃后能在 30 秒内定位到根因（现场转储），并且同一个 bug 不会出现第二次（回归测试）。**

## 三、代码量路线

Linux 约 3000 万行，是 30 年、上万人的积累。我们不假装能"一次写完"，而是把架构做成**能无痛长大的形状**：

| 阶段 | 规模 | 内容 |
|---|---|---|
| 核心期（M0–M4） | 3 万行 | 引导、内存、调度、中断、syscall、最小驱动 |
| 可用期（M5–M7） | 20 万行 | 块层、VFS、ext2/LumiFS、网络栈、USB 输入、显示、POSIX 兼容 |
| 覆盖期（M8+） | 数百万行 | 驱动大扩充（每类设备一个驱动 crate）、更多文件系统、虚拟化、电源管理、安全模块 |
| 长期 | 千万行级 | 硬件生态、架构移植（ARM64/RISC-V）、性能优化、形式化验证关键路径 |

> 规模不是目标，"能持续加东西而不崩"才是目标。每一万行都必须带着测试进来。

## 四、地址空间

```
0x0000_0000_0000_0000  用户空间（每进程独立 PML4）
0x0000_7FFF_FFFF_FFFF
0xFFFF_8000_0000_0000  内核直接映射（全部物理内存，2 MiB 大页）
0xFFFF_C000_0000_0000  vmalloc 区（内核模块、大缓冲）
0xFFFF_E000_0000_0000  内核镜像 + per-CPU 数据
0xFFFF_FFFF_FFFF_FFFF
```

- 内核映射在每个进程的页表里都有一份（宏内核惯例），切 CR3 不用换内核映射。
- 用户态指针进内核必须先过 `copy_from_user` 校验（范围、可读、不跨内核区）——
  这是 Linux 几十年补出来的教训，我们从第一天就做。

## 五、子系统边界（谁不许调谁）

```
arch/        只被上层调用，自己只依赖 core
mm/          依赖 arch；不许依赖 fs/net
kernel/      调度、线程、syscall 分发；依赖 mm/arch
fs/ net/ drivers/   依赖 kernel/mm；互相之间只通过 VFS / netdev / block 接口
```

反向依赖（fs 调 net、driver 调 VFS）一律编译期禁止：用 crate 依赖图强制，
不靠自觉。

## 六、模块化：一个子系统一个 crate

内核最终是一个二进制，但源码按 crate 切：

```
karch   kmem   kvm   kpt   kheap   kslab   kfault   ksched   kipc
kfs     knet   kdev   kuser   klinux   kqa(测试)
```

已经落地的（截至 M3）：`kmem` `kvm` `kpt` `kheap` `kslab` `kfault` `ksched` `kfs`。

内核内的模块（M3 起）：`arch`（GDT/TSS/switch_to/IrqSpinlock/SMP+AP 跳板）、
`intr`（IDT/PIC/PIT/ACPI 发现/LAPIC+IOAPIC/APIC 定时器/RTC 基准/异常/探针）、
`task`（任务表/调度/抢占）、`syscall`（int 0x80）、`mm`（帧/堆/页表）。

SMP 现状（M4）：四个核全部上线，各自持有独立内核栈与 GDTR/IDTR/LAPIC 定时器；
IPI 广播已可用。但**调度器仍然只在 BSP 上跑**——`task` 模块是单核实现
（一个全局任务表 + 一个 current），要做每核运行队列得等 M6。

存储与程序加载现状（M5/M6）：`dev/ata` → `fs`（kfs + IrqSpinlock）→ `fd` → `exec`（kelf）。
地址空间（M6）：每个用户进程一张 PML4，低半区空、高半区（256..511）共享内核；
上下文切换时写 CR3。ELF 按 `p_vaddr` 原样加载，用户栈每进程私有。
M7 补上了进程资源的两块：**fd 表进 `Task`**（每进程一张，8 项）、
**等待队列 + 管道**（真 `Blocked` 状态，不再靠 yield 轮询）、
以及**退出回收**（`reap` 走一遍低半区把页表和用户页还给帧分配器）。

M8 加了两块：**可写文件系统 LumiFS（redo 日志）+ 写回块缓存**，
以及**PCI 枚举**（驱动层的入口）。存储的落法是两块盘分工：
主盘 ext2 只读（执行用）、从盘 LumiFS 可写（数据与实验用），
中间夹 `kbcache`。

还共用的：块设备锁（`IrqSpinlock`）、全局调度器（仍只在 BSP 上跑）。
调度器下移到每核是 SMP 调度的前提，排在 virtio/DMA 之后。

**一处偏离原计划**：`kint` 没有做成独立 crate。IDT/PIC/PIT 的正确性只能在真机上验证
（宿主机单测测不出"中断门压栈顺序对不对"），所以这部分直接写在 `lumikernel/src/intr/`；
其中**可以**脱机验证的部分——向量语义、错误码位解码——抽成了 `kfault`。
同理 `kalloc` 拆成两层：`kheap`（大块堆，4 MiB 起）+ `kslab`（小对象，8 档）。

好处：
- 编译期就能挡住跨层乱调（crate 之间没有依赖就调不到）；
- 每个 crate 都能在宿主机 `cargo test`，硬件用 mock；
- 十个人并行改不同 crate，不会互相踩文件。

## 六点五、M9 新增的三层（Linux 兼容）

```text
用户态（busybox / 任意 musl 静态程序）
      │  syscall 指令（MSR: EFER.SCE / STAR / LSTAR / FMASK）
      ▼
arch/syscall_entry.S ── 换栈 + 手工拼 InterruptFrame ──▶ trap_return（与中断共用）
      │
      ▼
linux/            系统调用层：uaccess（用户指针）/ fs / mem / proc / trace
      │
      ▼
vfs.rs            统一命名空间：/ ext2（只读）、/data LumiFS、/dev 合成设备
      │
      ├── fs/     ext2（含符号链接解析）
      ├── fs2.rs  LumiFS（可写）
      └── pipe.rs 管道
```

三条边界：

1. **`linux/` 不直接碰页表**。所有用户指针都经过 `uaccess`，它只做两件事：
   按页验证（探针 + 页表权限位）、逐字节搬运。任务退出、页表复制这些事归 `mm/`。
2. **`vfs` 不认识 fd**。它只回答"这条路径对应哪个对象"。
   fd 表（`fd.rs`）负责"谁打开了它、偏移多少"。两层分开，`fstat` 与 `ls`
   才必然看到同一份数据。
3. **`klinux` 不碰硬件**。它只是 ABI 的字节级描述（`struct stat` 144 字节、
   `dirent64` 的 `d_reclen` 对齐规则、路径规范化），因此能在宿主机上跑 23 个单测。

## 六点六、M10 新增：两条引导链与 SATA

```text
UEFI 固件 ──▶ \EFI\BOOT\BOOTX64.EFI（boot/efi，Rust → PE32+）
                │ ① 内核以 PE 段嵌在装载器里，拷到物理 1 MiB
                │ ② UEFI 内存图 → E820（放物理 0x9000）
                │ ③ ExitBootServices（先换自己的栈）
                └ ④ iretq → 0x100000

BIOS 固件 ──▶ stage1（512B）──▶ stage2（实模式 → 长模式）──▶ 0x100000
                                        │ 自己探 E820，写 0x9000
                                        └ 交棒方式与 UEFI 完全一致

0x100000 ──▶ boot.S：建页表 → 切 CR3 → 跳高半区 → kmain(e820)
```

两条链在 `0x100000` 汇合，`boot.S` 之后**没有任何分支**——这是刻意的：
引导方式越多，越要保证"汇合点之后只有一条路"，否则会出现"只在 UEFI 下才错"的 bug。

磁盘层（M10 起）：

```text
kfs / lumifs  ──▶ dev::ata（同名接口）
                     ├── 有 AHCI 控制器 → dev::ahci（DMA + PRDT + FLUSH CACHE EXT）
                     └── 否则            → ATA PIO（0x1F0 端口，老机器/虚拟机兜底）
```

同盘分区：UEFI 盘上是 `ESP + ext2 + LumiFS` 三个分区，装载器把 ext2 的起始 LBA
写进 E820 表头的空档，`dev::ata` 在读写时加这个偏移。BIOS 链不写 → 偏移 0 →
"ext2 独占一块盘"的老语义不变。

## 六点七、M11 新增：质量工程层（`kqa`）

```text
           ┌───────────── 判定（纯逻辑，宿主机可单测）─────────────┐
           │ kqa::rng    确定性随机（PCG32，同种子同序列）        │
           │ kqa::fault  "第 N 次失败"的纯状态机                  │
           │ kqa::soak   采样环 + 整数最小二乘（不用浮点）        │
           │ kqa::fuzz   26 个边界值 + 6 种变异                   │
           └───────────────────────┬──────────────────────────────┘
                                   │ 被内核调用
           ┌───────────────────────▼──────────────────────────────┐
           │ qa::fault   原子量实现（不加锁、不分配，OOM 现场可用）│
           │ qa::soak    采样空闲帧/堆/任务/fd → 回归             │
           │ qa::perf    TSC 计时 + 换算纳秒                      │
           └──────────────────────────────────────────────────────┘
```

两条边界：

1. **判定与硬件分离**。`kqa` 里没有一行 `unsafe`（`#![deny(unsafe_code)]`），
   也没有任何硬件访问——所以它能在宿主机跑 47 个单测。修一个"斜率算错了"的 bug
   不需要启动虚拟机（一次启动 2.5 分钟，成本差 100 倍）。
2. **注入判定不能依赖锁**。注入点就在"分配失败"的现场，那里可能拿不到锁。
   所以内核侧的实现全是原子量：`AtomicU8`（当前注入点）+ 原子计数（第几次、已注入几次），
   连打印都得限流（否则一次风暴就把串口刷满）。

## 七、明确的技术取舍

| 取舍 | 选择 | 理由 |
|---|---|---|
| 宏内核 vs 微内核 | **宏内核** | 与 Linux 同构，性能与生态模型一致 |
| 单核 vs SMP | 先单核，M3 上 SMP | 早期并发是 bug 温床，但接口按 SMP 设计 |
| 4 级页表 | 是 | 5 级增加状态空间，收益要 TB 级内存才体现 |
| 内核堆 | 大块 kheap + 小对象 kslab，全部显式失败 | 内核里不允许"内存不足就 panic" |
| 文件系统 | 先只读 ext2，再自研日志 FS | 先能读，再能写；写路径必须带日志 |
| 语言 | Rust（no_std） | 内存安全是宏内核最划算的稳定手段 |
| 驱动 | 内核态，按设备类型分 crate | 与 Linux 一致；靠窄接口 + IOMMU 兜底 |
