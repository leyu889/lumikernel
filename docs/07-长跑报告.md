# 连续长跑报告（S3）

> 目标：证明"跑久了不会漏"。做法不是等 30 天——那是日历时间，压不动——
> 而是把三件事同时做出来：
> **① 一个能真跑满 30 天的长跑模式**、**② 一次真实的连续运行**、
> **③ 一个负对照，证明检测器真的抓得到泄漏**。
> 没有 ③，②的"零漂移"就只是一种说法。

## 一、长跑模式（内核里）

`LUMI_SOAK=1` 构建出的内核在 58 项自检全绿之后**进入无限循环**，只能关机退出：
每轮做一组混合负载，每 `N` tick 采一次样，每 64 个采样点报一次回归。

负载刻意覆盖**五条会漏的路径**：

| 每轮做的事 | 覆盖的泄漏点 |
|---|---|
| 分配 8 页再归还 | 物理帧分配器位图 |
| `Box` / `Vec` 反复申请释放 | 内核堆的块合并与分裂 |
| `open → read → close` | fd 表、ext2 只读缓存 |
| `pipe` 建 → 写 → 读 → 两侧都关 | 管道缓冲、等待队列 |
| `vfs` 解析 + 目录快照 + 归还句柄 | VFS 目录槽 |
| 每 2000 轮 fork+exec+wait+reap | 页表、任务槽、退出回收 |
| 每 4000 轮 LumiFS 写 1 KiB + sync + unlink | 日志、块缓存、空闲块位图 |

采样间隔两个档：

- **正式**（`LUMI_SOAK=1`）：60000 tick = **10 分钟**，30 天 = 4320 个采样点；
- **演示/验收**（再加 `LUMI_SOAK_FAST=1`）：100 tick = **1 秒**。

判定逻辑不在内核里临时写——复用 `qa::soak` + `kqa::soak`（整数最小二乘，
宿主机有单测：`slow_leak_is_detected` 专门验证"每 1000 轮漏 1 页"能被抓到）。

## 二、负对照：先证明"抓得到"，再谈"没抓到"

同一份内核，只多一个编译开关 `LUMI_SOAK_LEAK=1`：**每 5000 轮故意漏 1 帧**
（`frames::alloc_frame()` 的结果直接丢掉，不回还）。

```
SOAK r=24998001 s=127 frames=243098 ...
```

| 项 | 数值 |
|---|---|
| 采样点 | 127 |
| 连续运行 | 127 秒 |
| 轮数 | 24 998 001 |
| 空闲帧 | 248059 → **243098**（−4961，与"127 秒 × 39 帧/秒"吻合） |
| 回归斜率 | **−39412‰**（每 1000 个采样点） |
| 内核中途判定 | `SOAK-REG ... verdict=drift` |
| 最终判定 | **检测到漂移** |

也就是说：**每秒漏几帧这个量级，127 秒内就会被判死**。所以下面那次"零漂移"
不是检测器瞎了；它真的没漏。

（顺带说明为什么不用"让内核漏一点再看"这种玩笑做法来反证：负对照是独立的
构建开关，正常镜像里那段代码根本不存在——`#[cfg(soak_leak)]`。）

## 三、正式运行：连续 30 分钟

命令（一条，可无人值守）：

```bash
LUMI_SOAK=1 LUMI_SOAK_FAST=1 python build.py     # 采样间隔 1 秒
bash scripts/soak30.sh --minutes 30              # 跑 30 分钟
python scripts/soak-report.py build/serial-soak.log
```

结果（`scripts/soak-report.py` 原样输出，日志见 `docs/证据/M11-长跑-30分钟-串口日志.txt`）：

| 项 | 数值 |
|---|---|
| 采样点 | **1812**（回归窗口 64，中途报回归 28 次） |
| 轮数 | **350 456 001** |
| 资源操作 | **6 308 208 018**（每轮 18 次） |
| 连续运行 | **1812 秒（30.2 分钟）** |
| 吞吐 | 3 481 351 操作/秒 |
| 空闲帧 | **248098 → 248098（差 0）**，全程范围 `[248098, 248098]` |
| 堆已用 | 5280 → 5280（差 0） |
| 任务数 / 打开 fd | 10 → 10 / 0 → 0 |
| 回归斜率 | 帧 **+0‰** / 堆 **+0‰** / fd **+0‰** |
| 中途判定 | 28 条 `SOAK-REG`，`drift` **0** 条 |
| 结论 | **零漂移（通过）** |

**1812 个采样点、2 亿次帧分配/归还，空闲帧一个都没少，而且范围是单点
`[248098, 248098]`——不是"首尾相同但中间抖过"，是全程恒等。**

### 一个必须写下来的观察

guest 的计时是 1812 秒，但宿主墙钟走了约 48 分钟。原因很具体：同期宿主在
编译源码包（rustc 把 CPU 吃满），VM 的 APIC 定时器被拖慢，于是"guest 的 1 秒"
比"宿主的 1 秒"长。所以：

- **本文所有"连续 X 秒"都以 guest 自己的 tick 计数为准**（`t=` 字段），
  与内核里 `timer::ticks()` 同源；
- 墙钟时间在宿主侧另外记录（`soak30.sh` 的心跳行），两者**不能混着比**。

这也顺带说明为什么长跑必须记 `t=` 而不是只看"跑了多久"：
一旦宿主有负载，两者的偏差可以到 1.6 倍。

## 四、真跑 30 天怎么做

```bash
LUMI_SOAK=1 python build.py          # 采样间隔 10 分钟（正式档）
bash scripts/soak30.sh --minutes 43200   # 30 × 24 × 60
```

`soak30.sh` 会：建一台独立的 `LumiKernelSoak` 虚拟机 → 挂上启动盘 → 启动 →
每分钟打一行心跳（行数 + 最后一条采样）→ 每 10 分钟留一份串口快照（防止关机丢尾巴）
→ 到点关机 → 调 `soak-report.py` 出结论。

几点是刻意的：

- **独立虚拟机**：长跑要"不被打断"，而 `vmtest-efi.sh` 每次都会关机重启，
  共用一台会互相踩（VBox 的介质注册表按 UUID 记账）。
- **串口快照**：VBox 的 file 后端在 poweroff 时会丢掉还没刷盘的尾部，
  所以定时 `cp` 一份，最后用快照分析。
- **每次开机都是同一个镜像**：不依赖任何外部输入，因此"第 29 天出的问题"
  可以在第 1 天复现。

## 五、口径与边界（必须写清）

1. **"30 天等效"是工作量等效，不是日历等效。**
   本次连续运行的真实时间是 30 分钟；它执行的操作数换算成
   "30 天里每秒多少次操作"见上一节。日历时间压不动，这一点不糊弄。
2. **温度/时钟漂移类问题测不出来。** 30 天连续跑还会暴露晶振漂移、
   RTC 累积误差、长时间不重启的碎片化——这些只有在真实 30 天里才会出现，
   本文不做任何声称。
3. **两个采样档的负载强度不同**：正式档每 10 分钟一采，同样的墙钟时间里
   会做多得多的轮数（因为不打印）。所以"演示档 30 分钟的轮数"
   **不能**直接除以 4320 得到"30 天会做多少轮"。
4. **`LUMI_SOAK_FAST` 只改采样间隔，不改负载**——这是为了保持
   "演示抓到的漏"和"正式跑抓到的漏"是同一类东西。
