# 与 Linux 的对比（M11）

> 结论先说：**在系统调用与 IPC 上我们已经和 Linux 同量级（0.5–1.3 倍）；
> 在 `mmap` 与 `fork` 上差 14–200 倍，原因不是"代码慢"，而是两个明确的策略差异
> （我们不做懒分配、不做写时复制）。** 这份报告的目的是把差距变成待办清单，
> 而不是把数字修得好看。

## 一、方法（这部分比数字重要）

| 项 | 做法 |
|---|---|
| 被测对象 | `bench.elf`：6928 字节，`no_std`、零 libc、裸 `syscall`、`rdtsc` 计时 |
| 同一份二进制 | **同一个文件**分别放进去：LumiKernel 的 ext2 镜像（`/bin/bench`）与 Linux 的 FAT 盘（`/mnt/b/BENCH`） |
| 宿主 | 同一台物理机、同一个 VirtualBox 7.2.16、同一块 SSD |
| 计时 | `rdtsc`。两个 guest 跑在同一颗 CPU 上，**TSC 是同一个晶振**，周期数可以直接比。本文按内核校准的 **3499 MHz** 换算纳秒 |
| 采样 | 每边连跑 3 次，取**中位数**（单次会受调度抖动影响，例如 Linux 的 `fork_wait` 曾出现 2.4M 与 31M 两个差 13 倍的值） |
| Linux | Alpine Linux 3.21，kernel 6.12.13-0-virt，**2 vCPU / 2 GiB** |
| LumiKernel | v1.2.0（M11），**4 vCPU / 1 GiB**，UEFI + 自有 AHCI 驱动 |

**已知的不对等**（写在前面，别让人以为这是严格同配置）：

- vCPU 数量不同（4 vs 2）。下面所有指标都是**单线程**的，vCPU 数只影响"谁在跑"，
  不影响单次系统调用开销；但如果哪天做多线程对比，这条必须重新对齐。
- LumiKernel 只有一个控制台进程，Linux 有 30+ 个后台服务在跑（对单线程微基准影响很小，
  但确实存在）。
- 文件读的**对象不同**（`/bin/busybox` 1.1 MiB vs Alpine 的 `/bin/busybox` 908 KiB），
  比的是"每 4 KiB 热读"的单价，不是总吞吐。

## 二、结果

单位：**cycles/次**（括号里是换算成的纳秒）。中位数，各 3 次。

| 操作 | LumiKernel | Linux 6.12 | 比值 | 说明 |
|---|---|---|---|---|
| `getpid` | **408** (117 ns) | 734 (210 ns) | **0.56×** | 我们的系统调用入口更短：没有 KPTI、没有审计钩子、没有 seccomp |
| `write(/dev/null, 64B)` | **764** (218 ns) | 824 (236 ns) | **0.93×** | 基本持平 |
| `open+close` | 4564 (1304 ns) | **3451** (986 ns) | 1.32× | 差在路径解析：我们逐级线性扫描目录项，Linux 有 dcache |
| `read(/file, 4KiB)` | 3088 (883 ns) | **2063** (590 ns) | 1.50× | 我们走 ext2 + 64 块只读缓存；Linux 是页缓存 |
| `mmap+munmap(64KiB)` | 1 710 744 (489 µs) | **8426** (2.4 µs) | **203×** | **不可直接比**：我们在 mmap 时就分配并清零 16 页；Linux 只建 VMA，缺页时才给页 |
| `fork+exit+wait4` | 33 727 601 (9.6 ms) | **2 423 520** (693 µs) | 13.9× | **不可直接比**：我们整页复制地址空间；Linux 是 COW。另外我们的等待被时钟节拍量化（10 ms） |
| `pipe 1B 往返` | **1509** (431 ns) | 1370 (392 ns) | **1.10×** | 两次系统调用 + 两次上下文切换，几乎持平 |

### 换个角度看"同量级"

- 前三项（系统调用 + 文件元数据）落在 **0.5–1.5 倍**区间：这就是"同一量级"。
- 后两项差两个数量级，但**都是策略选择**：
  - `mmap`：Linux 的 2.4 µs 里**没有做任何实际工作**（只是插一个 VMA）；
    我们的 489 µs 里真的分配了 16 个物理页、清零了 64 KiB、建了两级页表。
    要公平比较，应该在**首次写**时计时（Linux 那时才会缺页）。这一项 M12 重做。
  - `fork`：我们复制整页（bench 进程约 10 页 → 10 次 4 KiB 拷贝 + 页表复制）；
    Linux 只复制页表并置只读。等实现 COW 之后这一项才会收敛。
- 还有一个**真实的慢点**：`fork_wait` 的 9.6 ms 里有约 10 ms 是等待被时钟节拍量化
  （父进程 `wait4` 阻塞后，子进程退出唤醒了它，但要等到下一个 tick 才真正切回去）。
  这是**能修的**，见下面的待办第 1 条。

## 三、内核侧另一组数（不用 bench，直接内测）

| 项 | 数值 |
|---|---|
| 帧分配 + 归还 | 41 ns/对 |
| 256 B 堆分配 + 释放 | 61 ns/次 |
| ext2 顺序读（热缓存） | 19–38 MiB/s（受 VBox AHCI 单条命令约 150 µs 限制） |
| LumiFS 1 KiB 写 + flush | 12.1 ms（含 5 次 `FLUSH CACHE EXT` 屏障） |
| 进程创建（装载 ELF + 建页表 + 建任务，不含等待） | 0.31 ms |
| 管道 1 KiB 写+读 | 184 ns |

`mmap` 这一项之前是 **174 万 → 现在 171 万**：M9 为了抓"一帧两用"加的全表扫描
（`frame_mapped_in`）原本在热路径上，这次已经移出，但每页仍要
"分配帧 + 清零 + `invlpg`"，在虚拟机里 `invlpg` 每次都是一次 VM exit，
这才是 489 µs 的主要来源。

## 四、待办（按性价比排序）

1. **`wait4` 立即唤醒**：退出路径唤醒等待者后置 `need_resched`，在当前系统调用
   返回前做一次调度，不再等 tick。预期把 `fork_wait` 从 9.6 ms 降到 ~0.5 ms。
2. **`fork` 写时复制**：页表置只读 + 缺页处理里复制。这是 M12 的大件。
3. **`mmap` 懒分配**：只记 VMA，缺页时才给页。改完这一项才谈得上和 Linux 比。
4. **ext2 读路径接块缓存**：现在只有一个 64 块的直连缓存，命中率取决于访问局部性；
   接上 `kbcache` 之后读吞吐应该能再上一个台阶。
5. **减少 `invlpg`**：批量 `mmap` 时只在最后刷一次 TLB（或者用 PCID + 惰性刷新）。

## 五、怎么复现

```bash
# LumiKernel 侧：bench 随内核镜像一起产出，自检块 57 会自动跑它
python build.py
bash scripts/vmtest-efi.sh out/LumiKernel-0.1-efi.img 80 bench 1 | grep -E '^[a-z_]+ [0-9]+$'

# Linux 侧：把 build/bench.elf 放进一个 FAT 盘，挂到任意 Linux 上
python tools/mkfat.py --file "BENCH=build/bench.elf" --output build/bench-fat.img --mb 8
# 进 guest 后：
#   mkdir -p /mnt/b && mount /dev/sda /mnt/b
#   /mnt/b/BENCH /bin/busybox /etc/hostname /dev/null
```

`bench` 的源码在 `bench/src/main.rs`（约 300 行，含注释）。它只依赖
`getpid / write / openat / read / lseek / close / mmap / munmap / fork / wait4 / pipe / exit_group`
这 12 个系统调用——**这 12 个是两边都实现了的最小交集**，也是这份对比能成立的前提。
