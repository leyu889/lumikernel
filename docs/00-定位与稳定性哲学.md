# 00 · 定位：什么叫「比 Linux 还稳定」

> 先把话说清楚，再开工。含糊的目标只会做出含糊的东西。

## 一、这句话得拆成两半

「写一个类似 Linux 的宏内核」——可以，而且已经在路上（见 `docs/02-路线图.md`）。
「比 Linux 还稳定」——要看你拿什么尺子量。

Linux 的稳定不是靠"代码写得好看"，是靠 **30 年 × 数百万台设备 × 每周上千个补丁** 磨出来的。
它在"什么硬件都能跑"这件事上，世界上没有第二个系统比得过。正面拼覆盖面，短期内我们必输。

但稳定 ≠ 覆盖面。稳定性有一把更硬的尺子：
**在同一批受支持的硬件与负载上，单位时间的故障次数是多少、每次故障的后果有多重、多久能定位到根因。**

按这把尺子，一个新内核完全可能赢——只要它不在同一个坑里摔倒两次。

所以本项目的目标是：

> **在受支持的硬件子集与 API 子集上，故障率更低、故障后果更轻、每次故障都能定位到根因；
> 并且在代码量长到 Linux 那个量级的过程中，这个性质不退化。**

## 二、宏内核的稳定性从哪来

我们选的是宏内核（驱动、文件系统、网络栈全在内核态，和 Linux 同构）。
这条路的天生弱点是"一颗老鼠屎坏一锅汤"。既然选了，就得把短板补在别处：

| 来源 | 做法 | 能消掉什么 |
|---|---|---|
| **内存安全** | 内核用 Rust，`unsafe` 只出现在 arch / MMIO / DMA 边界，每处必须有 `// SAFETY:` 证明 | 缓冲区溢出、UAF、double free、数据竞争 —— Linux CVE 里约 2/3 是这几类 |
| **窄接口** | 驱动只能通过 `BlockDevice`/`NetDev`/`IrqGuard` 等少数 trait 碰内核，不许直接动调度器和 VFS 内部结构 | 驱动"顺手改坏别人状态"的一大类崩溃 |
| **显式失败** | 所有可能失败的操作返回 `Result`/`Option`；内核里禁止 `unwrap`；OOM 不 panic | 静默失败、错误累积、内存不足时的连锁崩溃 |
| **分层强制** | crate 依赖图钉死调用方向（arch → mm → kernel → fs/net/drivers），反向依赖编译不过 | 循环依赖、初始化顺序错乱、子系统互相污染 |
| **可测** | 核心逻辑做成宿主机可单测的纯代码，硬件用 mock；模型测试 + 故障注入 + fuzz | 逻辑错误在合入前暴露，而不是在用户机器上暴露 |
| **现场可读** | panic 前把寄存器、栈回溯、当前任务、锁持有者写串口；重启后能复盘 | "崩了但不知道为什么"——这是稳定性最大的敌人 |
| **IOMMU** | 驱动 DMA 越界由硬件拦下（M5 起） | 驱动写飞内存把整机搞死 |

反过来说，下面这些**不是**我们追求的稳定来源：
更多驱动、更多文件系统、更多架构。那些是"覆盖面"，是 M8 之后靠时间堆的，不是靠设计。

## 三、可测量的稳定性指标（SLO）

每一条都在 `kqa` 里有对应脚本，不靠感觉：

| 编号 | 指标 | 目标 | 测量方法 |
|---|---|---|---|
| S1 | 内核 panic 次数 | **必须 = 0** | 所有测试与长跑日志里出现 `panic` 即失败 |
| S2 | 故障注入存活率 | **≥ 99.9%** | 注入分配失败 / 非法参数 / 队列满 / 随机中断 / 坏块，统计"系统仍可服务"的比例 |
| S3 | 30 天长跑内存漂移 | **0 页增长** | 每 10 分钟采样空闲页、slab 用量、句柄数，线性回归斜率 < 0.01 |
| S4 | 非法输入崩溃 | **0**（fuzz 24h） | syscall / IPC / 文件系统镜像 fuzz，任何 panic 或 hang 都算失败 |
| S5 | 崩溃定位时间 | **< 30 分钟** | 从拿到串口转储到定位到函数与行号 |
| S6 | unsafe 密度 | **≤ 5%** 且逐条挂证明 | `cargo geiger` + 人工清单 `docs/unsafe-register.md` |
| S7 | 回归覆盖 | 每个修过的 bug 都有对应用例 | `docs/回归用例.md` 与测试代码一一对应 |

> 「比 Linux 稳定」的判定方式：**同一台机器、同一组压力场景**，跑 Linux 和 LumiKernel，
> 比 S2/S3/S4 的数值。凡 Linux 有而我们没有的能力（比如 5000 种驱动），不参与比较——
> 这是范围声明，不是逃避。等覆盖面上来了，再比一次。

## 四、明确不承诺的事

1. **不承诺**兼容任意 Linux 硬件。目标硬件：VirtualBox/QEMU（开发与 CI）+ 一台真机（验收）。
2. **不承诺**完整 POSIX。先做能跑通 `busybox` 的那一层。
3. **不承诺**性能超过 Linux。目标是同一量级。
4. **不承诺**短期可用。这是以年计的项目，每个里程碑必须有可运行产物，但"能日常用"是 M8 之后的事。
5. **不承诺**"驱动崩了系统不倒"。宏内核做不到，硬说就是骗人。
   承诺的是：崩的概率更低、崩了能定位、同样的崩不会出现第二次。

## 五、代码量：怎么长到 Linux 那个量级还不烂

Linux 约 3000 万行，是 30 年、上万人的积累。我们不假装一次写完，而是把架构做成**能无痛长大**的形状：

- 一个子系统一个 crate，依赖方向钉死，加功能只能"往下加"，不能"往里塞"；
- 每个 crate 自带测试，新代码必须带用例进来；
- 硬件相关代码只在最薄的一层（arch / drivers），业务逻辑保持纯函数，能在宿主机跑；
- 驱动按设备类型独立成 crate，一个驱动坏了可以单独回退。

具体阶段见 `docs/02-路线图.md`。

## 六、为什么值得这么做

你自己有发行版（Deepseek OS），有桌面层（LumiOS），有安全工具（光盾）。
但底下那层永远是别人的。这个项目是唯一能把"从引导扇区到窗口管理器都是自己的"补齐的一环。
它不会明天就有用，但它每天都会变得更真。
