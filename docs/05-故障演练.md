# 故障演练：从串口转储到根因（S5）

> S5 的要求是"从拿到串口转储到定位到函数与行号 < 30 分钟"。
> 这一篇是**真实一次**的记录，不是演示：M11 期间跑性能基准时真的崩了，
> 而且是一个从现场完全看不出是栈问题的 bug。

## 一、现场（原样摘自串口日志）

```
=============== KERNEL EXCEPTION ===============
vector=14 (page-fault)  error=0xb
  cr2=0xffff80002ca00000
  pf: P=1 W=1 U=0 RSVD=1
  rip=0xffffffff80131299  cs=0x18
  rsp=0xffff800000680bf8  ss=0x20
  rax=0x0000000000000000 rbx=0xffff800000000000
  rcx=0x0000000000000200 rdx=0xffff80002ca00000
  rsi=0x0000000000000200 rdi=0xffff80002ca00000
  rbp=0xffffffff80131080 r8 =0x0000000000000000
  r9 =0x000000000002ca00 r10=0x000000000002ca01
  r11=0x0000000000000001 r12=0x0000000100000000
  r13=0x000ffffffffff000 r14=0x00000000ffff2000
  r15=0x000000002ca00000
  [stack+ 0] 0xffffffff801137ca  kernel_off=0x137ca
  [stack+16] 0x000000002c9fb000  kernel_off=0xac8fb000
  ...
```

触发条件：用户态 bench 程序连续做 2 万次 `mmap(64 KiB) + munmap`。

## 二、四步定位（这才是 S5 真正要的能力）

**第 1 步：先看 error 码，别猜。**
`error=0xb` = `P=1 | W=1 | U=0 | RSVD=1`。
`P=1` 说明**不是**"没映射"，而是"表项里有保留位"——即**页表项被写坏了**。
这一步就把排查范围从"内存管理"缩到"谁在写页表"。

**第 2 步：把这条地址的四级表项原样打出来。**
为此在崩溃处理器里加了一段"沿 CR2 走四级页表并打印表项值"的代码（现在常驻，
是 `intr/handler.rs` 的一部分）。结果：

```
[pt L3] idx=256 entry=0x0000000000151027
[pt L2] idx=0   entry=0x0000000000152027
[pt L1] idx=357 entry=0xffffffff8010f6cf      ← 这不是页表项
```

`0xffffffff8010f6cf` 是一个**内核代码地址**。直接映射的第 357 项（覆盖 714 MiB）
被写成了一个返回地址。

**第 3 步：用栈顶返回地址反汇编。**
崩溃转储里的 `[stack+0]` 就是返回地址（这是 M11 新加的：栈顶 12 个字 + 相对内核基址的偏移）。
`0x137ca` → `objdump -D -b binary -m i386:x86-64 --start-address=0x13740`：

```asm
137bd: lea    (%rdx,%rbx,1),%rdi   ; rdi = 物理地址 + 直接映射基址
137c1: mov    $0x1000,%edx         ; 4096 字节
137c6: xor    %esi,%esi            ; 填 0
137c8: call   *%rbp                ; → memset
```

也就是 `kpt::map` 在给**新分配的页表页**清零。而这一页自己的直接映射却坏了。

**第 4 步：对照 `.bss` 的物理布局。**
`boot.S` 里静态页表的排布是：`pml4 → pdpt_low → pdpt_kernel → pdpt_direct → pd_1g → stack(64 KiB)`。
`pd_1g` 的正下方紧邻**内核栈**。栈从 `stack_top` 向下长——**溢出时第一个踩到的就是 `pd_1g` 的尾部**，
而 `pd_1g[357]` 距数组末尾正好 1240 字节。

结论：**boot 栈溢出 1.2 KiB，把直接映射的页表项写成了返回地址。**

## 三、验证与修复

不靠推理结案，靠**量**：

1. 在 `boot.S` 里、`.bss` 清零之后，把 `[__stack_canary, stack_top-4KiB)` 全部填 `0x5A`；
2. 自检最后扫一遍，找第一个非 `0x5A` 的字节 → 高水位；
3. 结果：**65 KiB / 64 KiB（102%）** —— 与原假设完全吻合。

修复三件事：

- 栈从 64 KiB 提到 **256 KiB**；
- 在栈与页表之间插入 **4 KiB 金丝雀页**（`__stack_canary`），溢出先踩它而不是踩页表；
- 新增自检项 `stack`：打印高水位、检查金丝雀，超过 60% 就报 FAIL。

修复后：`[ OK ] stack: 高水位 65 KiB / 256 KiB (25%), 金丝雀完好`。

## 四、这次演练暴露的两个工具缺口（已补）

| 缺口 | 补法 |
|---|---|
| 崩溃现场只有寄存器，没有"谁调用的" | 转储栈顶 12 个字 + `kernel_off`（相对 `0xffffffff80100000`），可直接喂给 `objdump -b binary` |
| RSVD/权限类故障看不出"表坏了还是标志位错了" | 转储 CR2 的四级页表项原始值 |

## 五、时间账（诚实版）

| 阶段 | 耗时 |
|---|---|
| 复现 + 确认不是偶发（3 次启动，每次约 2.5 分钟） | ~8 分钟 |
| 上面四步定位（含加两处诊断代码并重新构建 2 次） | ~14 分钟 |
| 修复 + 验证（加金丝雀、扩栈、跑满 58 项） | ~18 分钟 |

**从拿到转储到指出"boot 栈溢出踩坏 pd_1g"约 14 分钟**，落在 S5 的 30 分钟以内。
真正花时间的是前后两次"重新构建 + 启动虚拟机"（每次 2.5 分钟），
所以 M12 要做的第一件事是把"构建 + 启动 + 抓日志"压到 30 秒以内（用 QEMU 的 `-kernel` 直启）。
